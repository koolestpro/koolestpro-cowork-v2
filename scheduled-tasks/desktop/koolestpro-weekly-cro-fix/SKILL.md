It is essentially never one of the fonts already loaded on the page or available on Google Fonts, so retyping the brand name in a similar-looking web font and calling it the logo is exactly the recreation this rule bans — it reads as close-but-wrong, which is a worse tell than an icon mismatch since text is what people read first. Treat every logo as an image asset regardless of whether it's icon-based or text-based: download the real PNG/SVG and embed it as a real `<img>`, never as live HTML/CSS text. This applies to any other brand mark too (badges, seals, trust icons) — same rule. Include the real logo download as an explicit step in the DeepSeek task spec's NOTES section so it isn't left to guesswork. If the real logo genuinely can't be retrieved (dead link, blocked, or the live site is text-only with no logo file), say so plainly in the run summary rather than inventing one silently — a text-only real header is a fact worth carrying into the rebuild as-is. A rebuild with a subtly-wrong recreated logo undermines the entire "this is genuinely your page, fixed" CRO Fix pitch.
- **Image aspect-ratio integrity (2026-09-04 -> corrected 2026-09-07, hard rule).** Before using `object-fit:cover` on any container that composites a real screenshot or product photo, check the container's actual rendered aspect ratio against the source image's real aspect ratio. A Caraway run shipped `object-fit:cover` on a `flex:1` container whose aspect ratio (~0.89:1) was nowhere close to the source photo's (~1.16:1), which hard-cropped/zoomed the photo and read as "not the same image." If the ratios don't reasonably match, use `object-fit:contain` on a contrasting-background plinth (reads as deliberate premium framing, not empty space) or resize the container to actually match the image. Never ship a cover-fit container you haven't checked this way — verify on the real rendered export, not the markup.

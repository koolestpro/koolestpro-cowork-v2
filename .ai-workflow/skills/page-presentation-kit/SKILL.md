# Page Presentation Kit

Take a real, working page — anything with a URL or local HTML file — and produce the visual assets someone needs to show it off: device mockups, a combined presentation graphic, and optionally a short walkthrough video. This skill has exactly one job. It doesn't write captions, doesn't know about anyone's content pipeline, and doesn't assume where its own output belongs — every one of those things is the calling project's responsibility, not this skill's.

## Why it's built this way

The whole point of a mockup is to make a real page look good *while staying honest about what the page actually is*. That's why screenshots are captured for real (Playwright, not imagined) and composited into frames with plain code (HTML/CSS or a calibrated perspective warp) rather than regenerated by an image model — an AI model asked to "redraw this screenshot inside a laptop" will happily invent slightly different text, spacing, or UI details, which is fine for a marketing ad but actively bad for something meant to prove a real page was built. Image generation still has a real role here (the *backgrounds*/scenes around the real screenshot), it just never touches the actual page content.

This skill is also deliberately portable. It gets installed once and used across every project — which only works if it never assumes it knows where to save things. Every run starts by reading the current project's own instructions for that.

## Step 0 — Find out where output belongs (always do this first)

Look at the current project's `CLAUDE.md` (already loaded into context automatically — no need to search for it) for a section called **"Page Presentation Kit — Export Routing"**. It will say where mockups/video/combined graphics go, and any naming convention to follow.

- If that section exists, follow it exactly.
- If it doesn't exist in the current project, default to `./page-presentation-kit-output/{page-slug}/` in the current project and tell the user you used a default — don't fail, and don't guess at a "smarter" location.
- Separately: the **reference library** (Step 4) has its own canonical home, `replo-rebuilds/page-presentation-kit-references/`, regardless of which project invoked this skill — see Step 4 for what to do if `replo-rebuilds` isn't connected in the current session.

## Step 1 — Capture real screenshots

Use the bundled `scripts/screenshot.py` (Playwright/Chromium — see `scripts/playwright-setup.md` for this sandbox's one-time ARM64 setup if it hasn't been done yet in the current environment).

```bash
python3 scripts/screenshot.py "https://example.com/page" desktop.png --width 1440 --height 900 --full-page --clean
python3 scripts/screenshot.py "https://example.com/page" mobile.png --width 390 --height 844 --full-page --clean
python3 scripts/screenshot.py "/path/to/local/page.html" desktop.png --file --width 1440 --height 900 --full-page
```

Capture both desktop and mobile viewports whenever both are relevant to the request — most "showcase this page" asks want both, since that's the whole selling point of "responsive." If the user only cares about one device, skip the other rather than generating something nobody asked for.

`--clean` dismisses cookie banners/popups before capture — use it by default; a mockup with a cookie banner across the hero looks like an accident, not a presentation.

## Step 2 — Pick the style

Read `references/mockup-style-patterns.md` before generating anything — it has the concrete composition detail for each of the seven styles below. Don't skip it and improvise from the names alone. Two of the seven aren't device mockups at all (`flat-full-page-screenshot`, `page-unroll-surreal`) — kept as first-class styles on purpose rather than squeezed into a mockup category, because not every useful presentation reference is a framed device shot.

| Style | What it is | Backend |
|---|---|---|
| `flat-browser-frame` | Clean browser chrome or plain phone bezel, no perspective | `scripts/composite_frame.py` (pure CSS) |
| `angled-3d-perspective` | Tilted 3D device shot, dark stage background | `scripts/composite_frame.py` (CSS 3D transform) |
| `multi-device-collage` | Desktop + mobile frames arranged together | `scripts/composite_frame.py` (needs both screenshots) |
| `dark-portfolio-shot` | Single frame, dark background, soft accent glow (also: stacked numbered case-study sections) | `scripts/composite_frame.py` (pure CSS) |
| `device-in-hand-lifestyle` | Real/photoreal hand-holding-device scene | `scripts/perspective_composite.py` (needs a calibrated background — see Step 2b) |
| `flat-full-page-screenshot` | No frame at all — the raw screenshot is the deliverable | none needed, or a minimal hairline border/shadow |
| `page-unroll-surreal` | Artistic, non-literal — page bends/unrolls out of the screen | `gpt-image` (real screenshot as reference input, one-off creative render) |

**If a reference image was given:** match it to the closest style above and use that style's backend, adapting colors/proportions toward the reference. If it genuinely doesn't fit any of the seven (not just "isn't a perfect match" — actually a different pattern), that's a legitimate reason to propose an eighth: say so, describe the pattern, and ask before inventing one on the spot. Note in your output which style you matched it to (or proposed).

**If no reference and no explicit instruction was given:** decide based on what's being shown — a single clean page usually wants `flat-browser-frame` or `dark-portfolio-shot`; a page meant to prove "this is responsive" wants `multi-device-collage`; a portfolio/case-study piece wants `dark-portfolio-shot` (stacked-sections variant) or `angled-3d-perspective`; a quick internal "here's the whole page" share wants `flat-full-page-screenshot`. Don't default to the photoreal lifestyle style or the surreal unroll style automatically — both are visually striking but setup- or context-dependent (see below), so only reach for them when the request specifically wants that feel or a reference calls for it.

### Step 2b — `device-in-hand-lifestyle` needs a one-time calibrated background

This is the one style that can't be built from pure code — a CSS gradient can't fake a hand. The pattern: generate the background scene (hand + device + environment, screen area left blank) with the `gpt-image` skill **once per device type**, calibrate its screen corner coordinates, save both to `assets/frames/`, and reuse that pair forever afterward. Full instructions are at the top of `scripts/perspective_composite.py` — read them before attempting this style for a device that doesn't have a calibrated background yet. If you're asked for this style and no calibrated background exists, do the one-time setup rather than quietly substituting a flat frame and calling it "lifestyle" — that would misrepresent what was delivered.

## Step 3 — Build the mockup(s) and combined graphic

Run the matching script from Step 2's table for each device you captured. If both desktop and mobile were captured and the request wants a single hero image, also produce a combined graphic — either via `multi-device-collage` directly, or by placing the two individual mockups side-by-side yourself if a different style was chosen for each.

## Step 3b — Mobile strip (`{slug}-mobile-strip.png`)

The whole mobile page laid out as side-by-side columns, so one image shows how the entire build reads on a phone. Every page build ships one, and it gets its own X post.

```bash
python3 scripts/build_mobile_strip.py "/path/to/page.html" \
  "{output}/presentation/{slug}-mobile-strip.png" --file
```

**It is a post, not a contact sheet.** Three rules, all from Ridwan and all already the defaults, so run the command above without flags unless there is a reason:

1. **Standard post dimension, always.** 1080×1350 by default. `--size square|story|landscape` for the other canvases.
2. **The canvas is covered completely, with no empty space, especially along the bottom.** The column count is picked automatically as the largest (max 5) that the page can actually fill, and the rest of the page is cropped. Showing every section matters less than covering the canvas: "as long as it covers the whole space, we can leave any missing part."
3. **A 12px gap between columns, never around the outside.** "A little gap inbetween to create distinctions." Without it a dark column running into a light one reads as one continuous page. `--gap` / `--gap-color` to override.

Column starts snap forward onto real section seams, so a column should not open mid-sentence. Look at the result before accepting it: check that no column boundary lands in the middle of a section and that nothing rendered as alt text. If the script reports unloaded images, check the actual pixels first, because lazy images report broken immediately after a tile capture even when they are fine.

`--mode contact-sheet` restores the old behaviour (whole page, exactly `--columns` columns, ragged bottoms, non-standard canvas). QA only, never the deliverable.

## Step 4 — Reference library (grows over time, lives in `replo-rebuilds`)

This skill keeps a shared, growing library of style references at `replo-rebuilds/page-presentation-kit-references/{style-name}/`, mirroring that project's existing `static-ads-references/{source}/` convention. It's not tied to any one project — treat `replo-rebuilds` as the canonical home whenever it's connected in the current session.

**Three ways references get added, and this skill should do all three without being asked twice:**

1. **Explicit dump:** the user says something like "add these images to references" — classify each image against the seven named styles (visually: does it read as flat/angled/collage/dark/lifestyle/full-page/unroll?) and save it into the matching subfolder. Remember two of those seven are intentionally not device mockups — a plain unframed screenshot or a surreal art piece isn't automatically an `inbox/` reject, it might just belong in `flat-full-page-screenshot` or `page-unroll-surreal`. Only use `inbox/` when it truly isn't any of the seven, and flag to the user if several `inbox/` images start looking like a real recurring pattern worth naming as an eighth.
2. **Reclassify on user correction:** if the user says an image belongs as its own style rather than shoehorned into an existing folder ("I still want this kept, it doesn't have to be a device mockup"), treat that as license to create the new named style folder immediately — don't just move the file, also add a section for it to `references/mockup-style-patterns.md` and a row to this file's style table so the new style is actually usable in future runs, not just archived.
3. **Auto-save on use:** whenever a reference image is supplied *for an actual generation run* (not just browsed), save a copy into the matching style folder too — the library should grow from real usage, not only from deliberate dumping sessions.

**If `replo-rebuilds` isn't connected in the current session:** fall back to saving references locally in the current project's own export-routing output folder (Step 0), under a `page-presentation-kit-references/` subfolder, and tell the user plainly that this copy won't be part of the shared library until `replo-rebuilds` is reconnected — don't silently pretend it went to the shared location.

## Step 5 — Optional video

If a walkthrough video is wanted, use `scripts/scroll_video.py` (same Playwright setup as Step 1):

```bash
python3 scripts/scroll_video.py "https://example.com/page" walkthrough.mp4 --width 1440 --height 900 --duration 8 --clean
```

Output is silent by default and uses an eased (not linear) scroll so it doesn't feel robotic. If narration or music is wanted, generate it separately with the already-connected `text-to-speech` / `sound-effects` skills (see the current project's video-gen setup if it has one) and mux it onto the video afterward — this script's only job is a clean, reliable scroll capture; don't fold audio generation into it and risk the whole run failing on an unrelated step.

If `ffmpeg` isn't available in the environment, the script saves a raw `.webm` instead of failing outright — say so plainly rather than presenting it as if the requested `.mp4` was produced.

## Edge cases

- **No CLAUDE.md routing section in the current project:** default to `./page-presentation-kit-output/{page-slug}/` and say so (Step 0) — never fail just because a project hasn't been configured for this yet.
- **`replo-rebuilds` not connected:** reference library falls back locally (Step 4); say so.
- **Page has almost no scroll height:** `scroll_video.py` handles this by holding on the hero for the full duration instead of erroring.
- **`device-in-hand-lifestyle` requested with no calibrated background yet:** do the one-time setup (Step 2b) rather than substituting a different style silently.
- **Reference doesn't clearly match any of the seven styles:** pick the closest and say which one you matched, or file it to `inbox/` if you're doing a pure library-dump rather than a live generation — don't force a bad match into a named folder just to avoid `inbox/`. If it's a real, coherent pattern that just isn't a device mockup (like `flat-full-page-screenshot` and `page-unroll-surreal` themselves started out), that's grounds to propose it as a new named style rather than defaulting to `inbox/` — see Step 4's "reclassify on user correction" note.
- **No screenshot possible (page requires auth, geo-blocked, etc.):** say so plainly rather than producing a mockup of a blank/error page and presenting it as done.


## Video capture and cover layout (2026-10-10, Ridwan)

- Capture scroll videos with `scripts/scroll_video_frames.py` (one exact scroll position + screenshot per frame at 30fps, then encoded). Live recording with stepped scrolling (`scroll_video_raw.py`) stuttered on the desktop/laptop video and is a fallback only.
- Videos must open on real content: no empty device screen, no idle hold. `frame_video.py` auto-trims any blank/static opening (max 3s, `--trim-start` overrides).
- Laptop + phone covers (video and still) put the phone overlapping the laptop's right side, drawn on top, sized to use the space. Geometry lives in `frame_video.py` `COVER_GEOM` / `overlap_cover_geometry()` and is shared by `build_device_still.py cover`.

You are running the weekly "static ad image" buffer-generation cycle for Ridwan Adekunle's (@koolestpro) local content pipeline. The project lives in the connected workspace folder "koolestpro-cowork-v2" (source of truth: ridwan_content_system_updated.html; local-first, no external posting tools).

⚠️ READ THIS FIRST — GENERATION METHOD IS NON-NEGOTIABLE (added 2026-07-18 after a rejected run).

The 2026-07-17 run shipped four ads that read as caption cards, not ads: a cream text panel stacked above a photo with the headline drawn by PIL. Ridwan rejected them. It happened because the run tried `--quality medium` gpt-image calls, hit the sandbox's hard ~45s per-command ceiling, and silently fell back to compositing text itself. Do not repeat this. Measured facts you can rely on (tested 2026-07-18, 1024x1536 portrait):

- `--quality medium` takes >44s and is ALWAYS killed by the ceiling. Never use it.
- `--quality low` takes 21-30s and renders headlines spelled correctly, photoreal, every time.
- Detached/background processes do NOT survive between bash calls — there is no fire-and-poll workaround. Every image must finish inside one command.

Therefore:
1. ONE gpt-image call per bash command. Four ads = four separate commands.
2. Always `--quality low --size 1024x1536`.
3. Headline, subline, badge and button text go IN THE PROMPT, quoted with "reading exactly:", so gpt-image renders them into the photograph. Full-bleed image, text sitting on the photo — never a separate text panel.
4. PIL/Pillow must NEVER draw ad copy. Its only permitted use is assembling the 2x2 combined-showcase.png from the four finished ads.
5. If a generation times out, re-run that one command. Never fall back to compositing, and never silently downgrade the deliverable — if something truly cannot be produced, say so plainly in the summary rather than shipping a lesser artifact that looks finished.
6. Read every generated PNG back and confirm the headline is spelled correctly and it reads as an ad before calling the run done.

Reference for what "right" looks like: outputs/static-ads/obvi_super-collagen-protein_20260711/ and outputs/static-ads/bebemoss_ginger-sleepy-bunny_20260717/. Full rules are in the project's CLAUDE.md under "Static Ad Image — Export Routing" → "GENERATION METHOD — HARD RULES".

**Product/packaging photos (2026-09-01, Ridwan's standing instruction):** whenever a real business's own product photo can be used instead of an AI-generated one, prefer the real photo — check the brand's live site first. When compositing a real photo, prefer a background-removed cutout over the raw studio/site photo where feasible, so it can sit cleanly against a contrasting background for a premium look, and never crop off part of the product — check the rendered crop, not just the source image.

**Logo and brand marks: use the real file, never let gpt-image invent one (2026-09-04, hard rule — see CLAUDE.md's "REAL BRAND ASSETS ONLY — NEVER RECREATE A LOGO" section, project-wide).** If an ad concept calls for the brand's logo or wordmark to appear anywhere in the composition (on packaging, a badge, a corner watermark), download the real logo file directly from the brand's live site (the header `<img>`'s real `src`/`srcset`, not a guessed favicon or a stale schema.org field) and composite that real file into the finished image — do not prompt gpt-image to "draw the [Brand] logo" and trust it to reproduce it accurately, since generated logos reliably drift from the real wordmark/icon in font, shape, or color. **This matters just as much for text-based/wordmark logos as icon-style ones (2026-09-04, Ridwan's clarification)** — a lot of business logos are just the brand name set in a distinctive custom typeface, and that typeface is part of the brand identity. gpt-image has no way to know that specific font, so a prompted-in wordmark will come out in some generic display font that's close-but-wrong — worse than an icon mismatch, since text is what people read first. If the product photo itself already shows the real packaging with the real logo printed on it (the common case), that already satisfies this rule — no extra step needed. Only extra care is needed when a design calls for the logo somewhere separate from the product photo itself (e.g. a corner badge), in which case composite the real downloaded logo file rather than prompting for it. If the real logo can't be retrieved, say so in the run summary rather than letting a generated approximation slip through unflagged.

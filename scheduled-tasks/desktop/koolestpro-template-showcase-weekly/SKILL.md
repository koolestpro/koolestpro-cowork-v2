Run 5 / 2026-07-31 — Ridwan reviewed the first real HALOS run (halos_pdp-01) and flagged THREE concrete defects, all now fixed at the script level (not just this one run's output — these are permanent fixes, read carefully since they change how you must capture/build every asset going forward):

  1. "The videos didn't finish scrolling, especially the desktop/laptop mock." Root cause, confirmed by extracting frames across the old laptop.mp4's timeline: identical content sat on screen from t=10s to t=20s (a real 10-second stall), then a completely different section appeared at t=29s with no visible transition. `scroll_video.py`'s in-page `requestAnimationFrame`-timed scroll loop is NOT robust in this sandbox — a heavy render load (especially a big desktop viewport) can stall the page's own main thread for real seconds, and once the stalled callback finally fires, it jump-cuts straight to the end instead of finishing smoothly. **Fix: use `scroll_video_raw.py` instead of `scroll_video.py` for every video capture in this task, no exceptions.** It drives scrolling with externally-stepped `page.evaluate(scrollTo) + page.wait_for_timeout()` calls from the Python side (immune to page-thread stalls) and captures at `device_scale_factor=1` for video specifically (quarters the pixel volume the renderer has to composite per frame, directly reducing stall risk — stills still use scale 2 elsewhere, no quality loss for video since frame_video.py scales into the bezel's screen rect anyway).
     - Usage: `python3 scroll_video_raw.py "<page>" raw_desktop.webm --file --width 1600 --height 966 --duration 26 --steps 48` (desktop) and the same with `--width 390 --height 855` for mobile. This produces a raw `.webm` only — no ffmpeg conversion needed as a separate step, because `frame_video.py` reads video files straight into its ffmpeg filter graph regardless of container (verified — `.webm` works directly as a `--video`/`--video2` input to `frame_video.py laptop`/`mobile`/`cover`). Do NOT add a manual webm-to-mp4 conversion step; it's redundant now.
     - Budget note: each `scroll_video_raw.py` call at `--duration 26 --steps 48` takes roughly 30-42 real seconds depending on sandbox load — comfortably inside the ~44s bash-call ceiling in testing, but if a call ever times out with no output file, retry once before assuming something is broken (the file is only written at the very end via `shutil.move`, so a timeout produces no partial file, unlike ffmpeg's partial-write failure mode).
